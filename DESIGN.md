# DESIGN.md
# 1. How do login and the two roles work?
I implemented authentication using signed JWT bearer tokens and salt-hashed passwords via bcrypt. Instead of maintaining persistent server sessions, the app uses stateless claims: the decoded token payload injects `req.user` with their database ID and assigned role (`customer` vs `admin`). Route security runs on a pipeline pattern—an initial gatekeeper verifies signature integrity (returning `401 Unauthorized` if absent or expired), while role-specific gates reject cross-role execution with `403 Forbidden`. Crucially, to prevent ID harvesting/enumeration attacks, any customer attempting to fetch or cancel a record belonging to another user receives an intentional `404 Not Found` rather than a `403`.

# 2. Which database did you choose, and why?
I chose MongoDB alongside Mongoose for two concrete architectural reasons: document symmetry and single-document ACID guarantees. The studio's entities—such as wall mural commissions carrying live dimensions/aspect ratios and ceramics tracking glaze recipes—map naturally to structured JSON without needing rigid multi-table joins. More importantly, MongoDB executes atomic operations at the document boundary natively, giving me race-condition safety on catalog items without having to configure an external distributed cache or run heavyweight relational table locks.

# 3. How do you stop two people from taking the same painting or date?
- **Paintings:** I avoided the classic "read-then-write" trap (querying status first, then saving). Instead, I rely on a single atomic operation: `Painting.findOneAndUpdate({ _id, status: 'available' }, { $set: { status: 'sold' } })`. Because the condition filter and update execute as an atomic transaction in the engine, only the thread that grabs the write lock while `status === 'available'` succeeds. The slower request simply finds 0 matching documents and immediately throws a 400 rejection.
- **Wall Dates:** On the backend, booking creation first runs a date collision check against records in `requested` or `confirmed` states. To elevate the user experience, I also exposed a read-only endpoint that streams booked dates to the frontend, disabling those dates directly inside the date-picker UI to catch conflicts before a request is ever dispatched.

# 4. What did you finish, what did you leave out, and what would you do next?
- **Finished:** The complete operational core: atomic one-of-a-kind art purchases with restock on cancellation; wall mural booking engine enforcing the 7–90 day window, cancellation minimums (>= 3 days), and live aspect-ratio pricing ($10–500 sq ft); custom ceramics pipeline with 14-day curing schedules and SVG glaze rendering; plus the full studio administrative approval lifecycle with dedicated empty, loading, and error states.
- **Left out:** Third-party cloud storage (AWS S3) for direct photo uploads, live payment processing (Stripe webhooks), and automated email/SMS dispatching, keeping the build focused entirely on the core assignment constraints.
- **What I'd do next:** I would implement a 10-minute pessimistic checkout reservation using a Redis TTL key (freeing paintings automatically if the buyer abandons checkout) and integrate iCalendar (.ics) exports for studio wall mural dispatching.
